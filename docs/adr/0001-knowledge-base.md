# ADR 0001. База знаний проекта: слои, источник истины, индекс

- Статус: принято
- Дата: 2026-11-27
- Контекст: агенты проекта уже имеют личную память (`agent_notes`), секретницу
  (`connections`), доменные метрики (`metric_definitions`) и runtime с broker-инструментами.
  Не хватает общего курируемого знания о проекте: кто покупатель, как устроен магазин,
  что показали исследования, какие правила действуют. Без него каждый агент заново
  «догадывается» о контексте, а ответы нельзя проверить по источнику.

## Решение

### 1. Три слоя вместо одной таблицы

| Слой          | Что это                                                                    | Кто пишет                            | Срок жизни                      |
| ------------- | -------------------------------------------------------------------------- | ------------------------------------ | ------------------------------- |
| Источники     | загруженные файлы, URL, вставленный текст; неизменяемые байты + метаданные | человек                              | постоянно, для цитат и аудита   |
| Дерево знаний | канонические страницы в Markdown, организованные в дерево                  | человек; агент — только предложением | долго, версионируется           |
| Индекс        | чанки, FTS, эмбеддинги                                                     | система                              | производный кэш, пересобирается |

Источник — доказательство, дерево — знание, индекс — ускоритель. Смешивать их нельзя:
страница может ссылаться на источник, но не является его копией, а индекс не является
источником истины.

### 2. Дерево знаний — единственный источник истины

- Агенты читают только дерево (через индекс), а не исходные файлы напрямую.
- Все ответы агента ссылаются на страницу (`knowledge_nodes.id`) и, если есть, на источник
  с локатором.
- Индекс можно удалить и пересобрать из дерева без потери знания. Пересборка запускается
  при смене модели эмбеддингов, изменении чанкинга или порче индекса.
- Изменения страницы фиксируются в `knowledge_revisions`; текущая версия — в самой странице
  для дешёвого чтения.

Почему не «файлы как есть»: файл нельзя отредактировать точечно, он не имеет структуры для
навигации, а извлечённый текст требует проверки человеком. Почему не «только вектор»:
вектор не редактируется, не показывает структуру и не даёт стабильных цитат.

### 3. Публикация только после подтверждения человеком

- Всё, что извлечено из файла или предложено агентом, создаётся в статусе `draft`.
- Агенты видят только `published`. Черновики не попадают ни в поиск агента, ни в контекст.
- Публикация — действие человека в UI (можно пакетно), с записью в журнал.
- Агент предлагает знание через `knowledge.propose`; предложение попадает в очередь
  подтверждения, а не в дерево напрямую.

Это защищает от «отравления» базы знаний галлюцинацией агента и от публикации
непроверенных цифр как факта.

### 4. Векторный поиск — pgvector в том же Postgres

- Расширение `pgvector`, тип `vector(1536)`, индекс HNSW с косинусной метрикой.
- Образ Postgres меняется с `postgres:17-alpine` на `pgvector/pgvector:pg17` в
  `docker-compose.yml` и в деплое; данные совместимы, пересоздание тома не требуется.
- Поиск гибридный: русский FTS (`to_tsvector('russian', ...)`) + вектор, слияние через
  Reciprocal Rank Fusion, затем фильтры и дедупликация по странице.
- Для артикулов и точных названий дополнительно `pg_trgm` по заголовку страницы.

Отдельная векторная БД (Qdrant, Weaviate) отклонена: второй store, второй бэкап, вторая
схема доступа и рассинхронизация с деревом при том же объёме данных (единицы тысяч чанков
на проект). pgvector даёт транзакционность, RLS и один бэкап.

### 5. Исходники — content-addressed blob store за интерфейсом

- Файлы лежат на диске/в S3 под ключом `{accountId}/{projectId}/{sha256}.{ext}`.
- В БД хранятся метаданные, хеш, размер, MIME и статус обработки.
- Одинаковые файлы дедуплицируются по хешу.
- Доступ к файлам — только через API с проверкой аккаунта; прямых публичных URL нет.
- Интерфейс `BlobStore` позволяет позже заменить диск на S3/MinIO без миграции данных.

## Последствия

- В `docker-compose.yml`, CI и на стенде нужен образ Postgres с pgvector.
- Появляются фоновые задачи: извлечение текста, чанкинг, эмбеддинги, переиндексация.
  Идемпотентность — по `content_hash`, повторный запуск не тратит токены.
- Эмбеддинги — единственная внешняя модель в контуре; провайдер скрыт за интерфейсом,
  чтобы позже заменить облако на локальную модель без изменения схемы.
- Часть знаний остаётся черновиками, пока человек не подтвердит: это осознанная цена
  проверяемости.
- `agent_notes` не превращаются в базу знаний: личная оперативная память агента и общее
  курируемое знание — разные сущности с разными правами.

## Отклонённые альтернативы

- Хранить только исходные файлы и искать по ним: нет структуры, нет точечного
  редактирования, цитаты нестабильны.
- Хранить только эмбеддинги: нечего показывать и редактировать, нет аудита.
- Писать знания агентами напрямую: риск отравления и потери доверия к ответам.
- Отдельная векторная БД: лишняя инфраструктура без выигрыша на нашем объёме.
