# PRD. База знаний проекта

- Продукт: ИИ-помощник продукт-менеджера интернет-магазина (Geniebox, WAVE DEV)
- Статус: к реализации
- Версия: 1.0, 2026-11-27
- Связанное решение: `docs/adr/0001-knowledge-base.md`
- Дедлайн демо-версии: 2026-11-28, 10:00 МСК

## 1. Проблема

Агенты платформы (управляющий, аналитик метрик, исследователь, маркетолог) работают с
проектом, о котором знают только то, что успели выяснить в диалоге. Знания о магазине
разбросаны: брифы, исследования, интервью, регламенты, цифры из отчётов, договорённости
команды. В результате:

- каждый новый диалог начинается с повторного объяснения контекста;
- ответы агента нельзя проверить: непонятно, откуда взялась цифра или вывод;
- знания живут в переписке и теряются при смене состава команды;
- агенты додумывают факты, которые человек считал известными.

Нужен общий курируемый слой знаний проекта, который человек наполняет и подтверждает,
а агенты используют как единственный проверяемый источник контекста.

## 2. Пользователи и сценарии

| Роль                                | Что делает с базой знаний                                                                   |
| ----------------------------------- | ------------------------------------------------------------------------------------------- |
| Продукт-менеджер (владелец проекта) | загружает материалы, редактирует страницы, подтверждает черновики, задаёт структуру         |
| Управляющий агент                   | читает знание перед планированием, ссылается на страницы в ответах, предлагает новое знание |
| Агенты-аналитики                    | ищут факты и правила проекта, используют цитаты в отчётах                                   |
| Администратор аккаунта              | видит состояние базы, права, ошибки обработки файлов                                        |

Ключевые сценарии:

1. PM загружает три файла исследования и один регламент. Система извлекает текст,
   предлагает страницы дерева. PM правит заголовки, убирает лишнее, публикует.
2. PM вручную создаёт страницу «Кто наш покупатель» и пишет её в редакторе.
3. PM спрашивает управляющего: «Почему упала конверсия в октябре?». Агент ищет по базе,
   находит страницу с сезонностью и страницу с определением конверсии, отвечает со ссылками.
4. Агент-исследователь замечает пробел: «нет данных о причинах возвратов». Он отправляет
   предложение (`knowledge.propose` / `report_gap`), PM видит его в очереди и либо создаёт
   страницу, либо отклоняет.
5. PM удаляет устаревшую страницу: она уходит в архив, перестаёт попадать в поиск,
   но остаётся в истории.

## 3. Цели и не цели

### Цели

- Дать человеку простой способ передать знание: файл, текст, ручная страница.
- Хранить знание в структурированном, редактируемом и версионируемом виде.
- Обеспечить агентам поиск с цитатами и запретить доступ к неподтверждённому.
- Сделать слой расширяемым: новые типы источников, модели эмбеддингов и агенты
  подключаются без переделки схемы.
- Уложиться в экономику: не переиндексировать неизменное, не отдавать агенту лишние токены.

### Не цели

- Не заменять секретницу: доступы, токены и пароли остаются в `connections`.
- Не хранить оперативные данные (остатки, заказы, ежедневные метрики) в базе знаний; для них
  есть доменные таблицы и инструменты.
- Не быть википедией с совместным редактированием в реальном времени и комментариями.
- Не строить собственный движок эмбеддингов и не обучать модели.
- Не давать агентам право публиковать знание без человека.

### 3.1 Соответствие ТЗ

| Требование ТЗ                                                                            | Как его закрывает база знаний                                                                                                                                                                  |
| ---------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Регулярно пополнять систему новыми исследованиями и интервью («закрытый контур»)         | импорт источника → черновик → публикация; цикл не требует релиза кода, версия и индекс обновляются по `content_hash`                                                                           |
| Объединить Метрику, конкурентный анализ, исследования и бэклог, перекрёстно их проверять | в базе живут исследования, конкурентный анализ, регламенты и ограничения данных; метрики, релизы и бэклог остаются в доменных таблицах, страницы ссылаются на них по id; агент получает цитаты |
| Параметры и метрики, влияющие на результат, настраиваемые                                | определения метрик остаются в `metric_definitions`; в базе хранятся редактируемые человеком правила интерпретации и пороги                                                                     |
| Ограничения данных и разрывы периодов должны явно показываться                           | у источника есть период и ограничения; цитата несёт период; агент обязан приводить оговорку вместе с выводом                                                                                   |
| Задача в бэклог с тегом «сгенерирована ИИ-помощником»                                    | вне базы знаний: доменный модуль бэклога получает основание и ссылки на страницы                                                                                                               |
| Сигналы PM на почту и в мессенджер                                                       | вне базы знаний: существующие уведомления и рассылки                                                                                                                                           |

База знаний не дублирует рядовые данные Метрики, релизы, задачи и продажи. Она хранит
знание о них: определения, правила, выводы исследований, ограничения и историю решений.

## 4. Модель данных

Все таблицы тенантные: `account_id`, `project_id`, RLS через `enableAccountRls`.
Доступ только через `AccountDb`. В проекте тенант — это аккаунт, поэтому `account_id`
играет роль `tenant_id` из гайдлайнов; отдельной колонки `tenant_id` нет.

### `knowledge_sources` — исходники

| Поле                         | Тип          | Назначение                                        |
| ---------------------------- | ------------ | ------------------------------------------------- |
| `id`                         | uuid         | PK                                                |
| `account_id`, `project_id`   | uuid         | тенант и проект                                   |
| `kind`                       | text         | `upload`, `url`, `text`                           |
| `title`                      | text         | исходное имя файла или заголовок                  |
| `mime`, `size_bytes`         | text, bigint | метаданные                                        |
| `sha256`                     | text         | дедупликация и идемпотентность                    |
| `blob_key`                   | text         | путь в `BlobStore`                                |
| `status`                     | text         | `processing`, `ready`, `failed`, `archived`       |
| `error`                      | text         | причина сбоя, ≤ 200 символов                      |
| `period_start`, `period_end` | date         | период данных источника, если применим            |
| `metadata`                   | jsonb        | метод, сегмент, уверенность, ограничения датасета |
| `created_by`                 | uuid         | автор                                             |
| `created_at`                 | timestamptz  |                                                   |

Уникальность: `(account_id, project_id, sha256)` — повторная загрузка того же файла
возвращает существующий источник.

### `knowledge_nodes` — дерево знаний

| Поле                           | Тип               | Назначение                                      |
| ------------------------------ | ----------------- | ----------------------------------------------- |
| `id`                           | uuid              | PK                                              |
| `account_id`, `project_id`     | uuid              | тенант и проект                                 |
| `parent_id`                    | uuid              | родитель, NULL для корня                        |
| `kind`                         | text              | `folder`, `page`                                |
| `title`                        | text              | 1–120 символов                                  |
| `body`                         | text              | Markdown, только для `page`, ≤ 200 000 символов |
| `status`                       | text              | `draft`, `published`, `archived`                |
| `position`                     | integer           | порядок среди соседей                           |
| `content_hash`                 | text              | хеш заголовка и тела, для индексации            |
| `source_id`                    | uuid              | источник, из которого извлечена страница        |
| `published_at`, `published_by` | timestamptz, uuid | кто и когда подтвердил                          |
| `created_by`, `updated_by`     | uuid              |                                                 |
| `created_at`, `updated_at`     | timestamptz       |                                                 |

Правила:

- `folder` не имеет тела и не индексируется.
- Циклы в дереве запрещены (проверка при перемещении, плюс защита в БД).
- `published` без `published_at` невозможен (CHECK).
- Уникальность `(account_id, id)`, чтобы дочерние ссылки оставались в границах тенанта.
- Архив — доменный статус, отдельного `deleted_at` нет. Жёсткое удаление страницы
  запрещено: архивный узел скрыт из дерева по умолчанию, исключён из поиска агента и
  остаётся в истории.
- Внешние ключи составные: `(account_id, project_id)` → `projects`, родитель →
  `(account_id, parent_id)` → `knowledge_nodes`; это не даёт связать узлы разных тенантов.

### `knowledge_revisions` — история

`id`, `account_id`, `node_id`, `revision` (int), `title`, `body`, `status`, `author_id`,
`author_kind` (`user`, `agent`, `system`), `created_at`. Уникальность `(node_id, revision)`.
Ревизия создаётся при каждом содержательном изменении; перемещение и смена `position`
историю не порождают.

### `knowledge_citations` — связь страницы с доказательством

`id`, `account_id`, `node_id`, `source_id`, `locator` jsonb
(`{"page": 3}` либо `{"section": "2.1", "charStart": 1200, "charEnd": 2040}`),
`quote` text (≤ 1000 символов), `created_at`.

### `knowledge_chunks` — производный индекс

| Поле                       | Тип          | Назначение                                |
| -------------------------- | ------------ | ----------------------------------------- |
| `id`                       | uuid         | PK                                        |
| `account_id`, `project_id` | uuid         | тенант и проект                           |
| `node_id`                  | uuid         | страница                                  |
| `position`                 | integer      | порядок чанка в странице                  |
| `heading_path`             | text[]       | хлебные крошки заголовков                 |
| `text`                     | text         | 200–3000 символов                         |
| `token_count`              | integer      | для бюджета контекста                     |
| `content_hash`             | text         | хеш текста чанка                          |
| `tsv`                      | tsvector     | generated: `to_tsvector('russian', text)` |
| `embedding`                | vector(1536) | NULL, пока не посчитан                    |
| `embedding_model`          | text         | модель, которой посчитан вектор           |
| `created_at`               | timestamptz  |                                           |

Индексы: GIN по `tsv`; HNSW (`vector_cosine_ops`) по `embedding`; btree
`(project_id, node_id)`.

### `knowledge_proposals` — очередь предложений агентов

`id`, `account_id`, `project_id`, `agent_id`, `kind` (`create`, `edit`, `gap`), `payload`
jsonb (`{"title", "body", "parentId", "nodeId", "reason"}`), `status`
(`open`, `accepted`, `rejected`), `resolved_by`, `resolved_at`, `created_at`.

### Хранилище исходников

Интерфейс `BlobStore`: `put(key, stream)`, `get(key)`, `delete(key)`. Ключ
`{accountId}/{projectId}/{sha256}.{ext}`. Реализация MVP — локальный диск (Docker volume),
позже S3/MinIO без изменения схемы.

## 5. Функциональные требования

### 5.1 Дерево знаний (P0)

- Создание папки и страницы, переименование, перемещение, архивирование, восстановление.
- Редактор Markdown с предпросмотром; автосохранение черновика.
- Статусы видны в дереве: черновик, опубликовано, архив.
- Публикация страницы; пакетная публикация выбранных черновиков — P1.
- Просмотр истории версий и восстановление версии как новой.
- Пустая опубликованная страница запрещена (минимум 1 непустой абзац).

### 5.2 Импорт источников (P0 — текст и Markdown, P1 — PDF/DOCX/XLSX)

- Загрузка файла `.md`, `.txt`, `.csv` (P0); `.pdf`, `.docx` (P1).
- Вставка текста вручную как источника (P0).
- Дедупликация по `sha256`: повторная загрузка не создаёт дубликат и не тратит токены.
- После загрузки — фоновая обработка: извлечение текста → разбиение по заголовкам →
  создание черновых страниц с цитатами → уведомление в UI.
- Ошибка обработки видна человеку с причиной и кнопкой «повторить».
- Ни одна извлечённая страница не публикуется автоматически.
- Ограничения загрузки: не больше 20 МБ на файл, белый список MIME и расширений,
  проверка фактического типа по содержимому, имя файла не используется как путь.
- Файлы лежат вне корня веб-сервера, не исполняются и не отдаются по публичному URL.
- Повторная загрузка защищена `Idempotency-Key`, эндпоинт ограничен rate limiter.

### 5.3 Чанкинг и индексация (P0)

- Структурный чанкинг по заголовкам: 400–700 токенов, overlap ~10%.
- В каждый чанк добавляется `heading_path` и заголовок страницы.
- Эмбеддинги считаются только для чанков опубликованных страниц, у которых изменился
  `content_hash`.
- Батчи до 64 чанков, ретраи с backoff, идемпотентность по `content_hash`.
- При смене модели эмбеддингов — фоновая переиндексация всех опубликованных страниц.

### 5.4 Поиск (P0)

- Гибридный: FTS (`russian`) + вектор, слияние Reciprocal Rank Fusion (k=60).
- Фильтры: проект, папка/поддерево, статус (для человека), дата обновления.
- Дедупликация результатов по странице: в выдаче одна страница с лучшим чанком,
  остальные чанки доступны при раскрытии.
- Быстрые точные совпадения: `pg_trgm` по заголовку и `ILIKE` по артикулам.
- Целевая задержка: p95 < 300 мс на проект до 5 000 чанков.
- Пустой запрос и запрос без результатов возвращают понятное состояние, а не ошибку.

### 5.5 Инструменты агента (P0; `knowledge.report_gap` — P1)

| Инструмент             | Риск   | Назначение                                                   |
| ---------------------- | ------ | ------------------------------------------------------------ |
| `knowledge.search`     | low    | поиск, возвращает 3–5 чанков с `nodeId`, заголовком, цитатой |
| `knowledge.read`       | low    | полная страница по `nodeId` для детального разбора           |
| `knowledge.tree`       | low    | оглавление опубликованных страниц для навигации              |
| `knowledge.sources`    | low    | список источников страницы с локаторами                      |
| `knowledge.propose`    | medium | предложение создать/изменить страницу                        |
| `knowledge.report_gap` | low    | сообщить о пробеле в знаниях                                 |

Правила:

- Все инструменты работают только с `published` и только в рамках проекта агента.
- `knowledge.search` не возвращает тело страницы целиком и не отдаёт больше 5 чанков.
- В результатах поиска и цитатах передаются период и ограничения источника. Если данных
  за период нет или в них разрыв, агент обязан сказать это явно и не строить вывод без
  оговорки.
- Ответ агента человеку содержит ссылки на страницы; UI превращает их в переходы.
- `knowledge.propose` уважает `agent_permissions` и режимы `auto/notify/approve/deny`;
  по умолчанию `approve`. Даже при `auto` предложение не публикуется без человека.
- Инструменты не имеют доступа к секретам и `blob_key`.

### 5.6 Управление пользователем (P1, минимальный UI — P0)

- Страница «База знаний» в навигации: дерево слева, редактор справа.
- Вкладки страницы: содержимое, источники, история.
- Очередь черновиков и предложений агентов с действиями «опубликовать», «отклонить».
- Индикатор состояния индексации: сколько страниц ждёт публикации и обработки.
- Поиск по базе с переходом к странице и подсветкой фрагмента.

### 5.7 Права и изоляция (P0)

Роли — роли аккаунта из `common/auth/account-role.ts`; отдельных ролей проекта нет.

| Роль             | Чтение                | Черновики и источники     | Публикация и предложения |
| ---------------- | --------------------- | ------------------------- | ------------------------ |
| `owner`, `admin` | да                    | да                        | да                       |
| `tech`           | да                    | да                        | нет                      |
| `viewer`         | только опубликованное | нет                       | нет                      |
| агент            | только опубликованное | через `knowledge.propose` | нет                      |

- Публикация и решения по предложениям — `@RequireAccountRole('admin')`.
- Создание и правка черновиков, загрузка источников — `@RequireAccountRole('tech')`.
- Чтение и поиск — любая роль, но `viewer` не видит черновики и архив.
- RLS на всех таблицах, тест изоляции аккаунтов на каждый новый модуль.

### 5.8 Экономика (P0)

- Переиндексация только по `content_hash`; неизменные страницы не тратят токены.
- В контекст агента — не более 5 чанков, полная страница — только явным `knowledge.read`.
- Лимит: не более 1 500 токенов знания на один шаг агента.
- Стоимость одного поиска без учёта эмбеддингов запроса — один SQL-запрос; эмбеддинг
  запроса кэшируется на время диалога по нормализованному тексту.
- Счётчик израсходованных токенов эмбеддингов пишется в журнал по проекту.

### 5.9 События, журнал и надёжность (P0)

- Значимые действия порождают события после commit: `knowledge.node_created`,
  `knowledge.node_updated`, `knowledge.node_published`, `knowledge.node_archived`,
  `knowledge.source_uploaded`, `knowledge.source_processed`, `knowledge.source_failed`,
  `knowledge.proposal_resolved`.
- Публикация, архивирование и решение по предложению пишутся в журнал действий в той же
  транзакции (`journal.record`).
- Извлечение текста, чанкинг и эмбеддинги — только в worker через очередь;
  HTTP отвечает 202 и статусом источника. Payload джоба содержит `tenantId` и `traceId`,
  `jobId` детерминирован (`knowledge:{sourceId}:{contentHash}`), заданы `attempts`,
  `backoff` и обработка `failed`.
- Сбой обработки не теряет источник: статус `failed`, причина, ручной retry.

### 5.10 Недоверенный контент и персональные данные (P0)

- Загруженный текст, страницы и цитаты — недоверенный контент. В промпт они попадают
  только в пользовательской части, в явных разделителях и с пометкой «данные, не
  инструкции» (тип `UntrustedText`), ссылки из них не открываются автоматически.
- Для ролей, читающих базу знаний, действует регрессионный набор prompt-injection кейсов:
  недоступные инструменты не вызываются ни при каком содержимом страницы.
- Персональные данные в базу не импортируются: при загрузке выполняется маскирование,
  подозрительные источники помечаются для проверки человеком.
- Перед отправкой текста провайдеру эмбеддингов выполняется псевдонимизация и маскирование;
  используются только провайдеры, не обучающиеся на переданных данных. Перечень
  провайдеров и категорий данных фиксируется в README.

## 6. API

Под `/v1/accounts/:accountId/projects/:projectId/knowledge`, за `AccountAccessGuard`.

| Метод | Путь                                         | Назначение                          |
| ----- | -------------------------------------------- | ----------------------------------- |
| GET   | `/nodes?parentId=&status=`                   | дерево и дети узла                  |
| POST  | `/nodes`                                     | создать папку или страницу          |
| PATCH | `/nodes/:nodeId`                             | заголовок, тело, родитель, позиция  |
| POST  | `/nodes/:nodeId/publish`                     | опубликовать (право владельца)      |
| POST  | `/nodes/:nodeId/archive`                     | в архив                             |
| GET   | `/nodes/:nodeId/revisions`                   | история                             |
| POST  | `/nodes/:nodeId/revisions/:revision/restore` | восстановить версию                 |
| POST  | `/sources`                                   | загрузить файл или вставить текст   |
| GET   | `/sources?status=`                           | список источников и статусов        |
| POST  | `/sources/:sourceId/retry`                   | повторить обработку                 |
| GET   | `/search?q=&parentId=&limit=`                | гибридный поиск                     |
| GET   | `/proposals?status=open`                     | предложения агентов                 |
| POST  | `/proposals/:proposalId/accept`              | принять и создать/изменить черновик |
| POST  | `/proposals/:proposalId/reject`              | отклонить                           |

Ответы поиска: `{ items: [{ nodeId, title, headingPath, snippet, score, sourceIds }] }`.
Списки (`/nodes`, `/sources`, `/proposals`, история) используют общий контракт пагинации
проекта с метаданными, а не голый массив. Все DTO описаны в Swagger.
Ошибки — в общем формате API, с кодами `KNOWLEDGE_NOT_FOUND`, `KNOWLEDGE_NOT_PUBLISHED`,
`KNOWLEDGE_CYCLE`, `KNOWLEDGE_SOURCE_FAILED`, `KNOWLEDGE_FORBIDDEN`.

Действия-переходы (`/publish`, `/archive`, `/retry`, `/accept`, `/reject`) оформлены как
подресурсы, по образцу существующих `metrics/:id/collect` и `agents/:id/pause`; это
осознанное исключение из общего правила «без глаголов в пути», зафиксированное проектом.

## 7. Нефункциональные требования

- Мультитенантность: `account_id` во всех таблицах, RLS, `AccountDb`, тест изоляции.
- Все записи — в транзакции вызывающего; фоновые задачи через существующие очереди,
  `outbox` и `scheduledTasks`.
- Импорт и индексация не блокируют HTTP-запрос: ответ 202 и статус источника.
- Логи: кто загрузил, кто опубликовал, какие страницы попали в ответ агента.
- ПДн: в базу не попадают персональные данные из `context/raw`; демо-данные обезличены.
- Мобильные браузеры: дерево сворачивается, редактор занимает весь экран.
- Конфигурация только через `src/config`: `EMBEDDING_MODEL`, `EMBEDDING_DIMENSIONS`,
  `EMBEDDING_BASE_URL`, `EMBEDDING_API_KEY`, лимиты загрузки. `process.env` вне config
  не читается.
- Миграция: `202611270003_knowledge.ts`, регистрация в `migrations/index.ts`, `up` и `down`
  реализованы. `CREATE EXTENSION IF NOT EXISTS vector` и `pg_trgm` выполняются в миграции
  ролью-владельцем; `down` удаляет таблицы, расширение не трогает.
- Цепочка зависимостей: `docker-compose.yml` и деплой переходят на закреплённый
  `pgvector/pgvector:pg17`, том `postgres-data` сохраняется.
- Строки интерфейса и ошибок — через i18n проекта (`ru` и `en`), не хардкодятся.
- Web: `apps/web` по feature-first структуре (`features/knowledge-*`,
  `widgets/knowledge-tree`), server-state — TanStack Query, формы — react-hook-form + zod,
  компоненты — shadcn/ui из `packages/ui`; дерево и редактор работают в мобильном браузере.
- Тесты: unit для сервисов, integration на реальном Postgres (RLS, поиск, миграции),
  e2e на поток «загрузил → опубликовал → агент нашёл»; провайдер эмбеддингов — fake,
  реальный API в CI не вызывается.
- Сторонние библиотеки (парсеры, клиент эмбеддингов, pgvector) перечисляются в README
  и в описании продукта.

## 9. Критерии приёмки

- Человек загружает `.md`, через минуту видит черновые страницы, публикует их, и они
  появляются в поиске агента.
- Агент отвечает на вопрос по опубликованной странице и указывает её в ответе.
- Черновик не находится инструментами агента и не попадает в контекст.
- Повторная загрузка того же файла не создаёт дубликат и не вызывает эмбеддинги.
- Пользователь другого аккаунта получает 404 на любой узел чужого проекта.
- Предложение агента не меняет дерево до подтверждения человеком.
- `viewer` не видит черновики, `tech` не может опубликовать страницу.
- Содержимое страницы с prompt injection не заставляет агента вызвать недоступный инструмент.
- Поиск по 2 000 чанкам отвечает за p95 < 300 мс локально.
- Тест изоляции аккаунтов проходит для узлов, источников, чанков и предложений.
- Удалённая (архивная) страница исчезает из поиска, но остаётся в истории.

## 10. Метрики успеха

- Доля ответов агента со ссылкой на страницу: ≥ 80% в демо-сценариях.
- Время от загрузки файла до опубликованной страницы у PM: < 3 минут.
- Доля черновиков, опубликованных без правок: < 50% (иначе извлечение слишком грубое).
- Стоимость индексации 100 страниц: измерима и указана в README.
- Ноль случаев попадания черновика или чужого проекта в контекст агента.

## 11. Риски

| Риск                                                  | Смягчение                                                                                |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Смена образа Postgres ломает стенд                    | проверить обновление на стенде до дедлайна, оставить прежний том и откат                 |

## 12. Открытые вопросы

- Нужны ли читателям без права публикации личные черновики, невидимые остальным?
- Хранить ли цитаты на уровне чанка, а не страницы, для более точных ссылок?
- Нужен ли экспорт всего дерева в один Markdown-архив для бэкапа и переноса?
- Какая локальная модель эмбеддингов подойдёт для закрытого контура и сохранит ли она
  размерность 1536 (иначе нужна переиндексация и вторая колонка).
- Кто отвечает за регулярный пересмотр знаний: нужен ли `review_due_at` и напоминания
  PM о страницах, которые давно не подтверждались.
