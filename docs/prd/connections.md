# PRD. Раздел «Подключения»: секретница проекта и ввод доступов

- Продукт: ИИ-помощник продукт-менеджера интернет-магазина (Geniebox, WAVE DEV)
- Статус: к реализации
- Версия: 2.1, 2026-11-27
- Связанные документы: `docs/adr/0002-connections-import.md`, `docs/prd/knowledge-base.md`
- Код: `apps/api/src/modules/connections`, `apps/api/src/secrets`, `apps/api/src/modules/runtime/llm`,
  `apps/web/src/features/project-settings/ui/keys-settings.tsx`,
  `apps/web/src/widgets/project-onboarding/ui/onboarding-connections.tsx`,
  `packages/types/src/project-operations.ts`

## 1. Проблема

Платформа расширяемая: аналитик читает метрики, исследователь — интервью, дальше появятся
маркетолог, поддержка, закупки. Каждому агенту нужны доступы к сервисам магазина: Метрика,
платежи, бот, база, серверы, код. Все доступы живут в одном месте — секретнице проекта.

Сегодня секретница работает, но пользоваться ею неудобно:

- подключить сервис можно только в мастере онбординга; в настройках проекта есть лишь список
  ключей и «перевыпустить»;
- доступы вводятся по одному полю и по одному сервису — человек же получает их списком, файлом,
  таблицей или просто парой «логин и пароль» в переписке;
- два разных раздела «Подключения» в продукте: страница `/connections` (только Метрика) и
  вкладка «Ключи доступа» (все сервисы).

Ключевое требование, из которого следует всё остальное: **человек не должен подгонять свои
доступы под нашу схему полей**. Он вставляет или прикладывает то, что у него есть — `.env` от
разработчика, `.txt`, `.md`, кусок тикета, две строки «логин: пароль» — а разбирается с этим система. Если из текста
непонятно, к какому сервису относится пара значений, система не угадывает и не выбрасывает их,
а спрашивает человека в диалоге.

Требования к разделу:

1. Ввод принимает любой текст: свободный текст, `.env`, `.txt`, `.md`, отдельные значения.
2. Смысл разобранного определяет модель; запись в секретницу — только после проверки кодом и
   подтверждения человеком.
3. Значение секрета не попадает в логи, ответы API, журнал, Redis и в контекст моделей.
4. Раздел расширяется записью в реестре провайдеров: новый сервис не требует нового экрана.
5. Доступ к секретам — только у роли `tech` и выше; агенты получают доступ через runtime, а не
   через UI.

## 4. Пользователи и сценарии

| Роль                   | Что делает в разделе                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| Владелец / админ       | подключает сервисы, перевыпускает ключи, отключает всё (danger zone)          |
| Технический специалист | то же, кроме «отключить все сервисы»; обычно он и вводит доступы              |
| Наблюдатель            | видит только сводку покрытия, ключи и значения ему недоступны                 |
| Агенты                 | в UI не ходят; получают доступ через runtime и `ConnectionSecrets` в worker'е |

Сценарии:

1. **Пара «логин и пароль» без подписей.** Владелец вставляет две строки из переписки. Система
   видит два значения без имени сервиса, не угадывает и спрашивает: «К какому сервису относится
   эта пара?» со списком каталога. Он выбирает ЮKassa, распределяет `shop_id` и `secret_key`,
   сохраняет. Если сервиса в каталоге нет — диалог предлагает пропустить (в P1 — «свой сервис»).
2. **Разработчик прислал `.env`.** 12 переменных: Метрика, Telegram, PostgreSQL. Владелец
   загружает файл, видит три готовые группы, четыре нераспознанных значения, отвечает на два
   вопроса, сохраняет три подключения одним действием.
3. **Список из переписки.** Разработчик прислал сообщение, где каждый сервис описан абзацем:
   «ЮKassa: shop_id 123456, ключ live_…». Владелец копирует его в поле, система разбирает
   строки: подпись, двоеточие, значение.
4. **Ключ нельзя отправлять в чат.** Тимлид создаёт одноразовую ссылку, разработчик вводит
   доступ сам, владелец получает письмо о результате проверки.
5. **Токен отозвали.** Агент получает `UNAUTHORIZED`, владелец видит «Требуется новый ключ»,
   вставляет новый, старый живёт ещё 5 минут и уничтожается.

## 5. Устройство раздела

### 5.1 Место в продукте

Вкладка «Подключения» в настройках проекта — вместо «Ключи доступа». Всё принадлежит проекту:
RLS по `account_id`/`project_id`, агенты проекта пользуются этими доступами. Глобальная
страница неизбежно смешала бы проекты и роли.

`/connections` превращается в редирект на `настройки активного проекта → Подключения`. Легаси
`connectionsApi` (`/v1/connections`, только Метрика) удаляется после переноса: провайдер
`yandex_metrika` в реестре уже есть.

### 5.2 Список подключений

- Шапка: «Команда видит N% проекта» из `GET summary`, покрытие по шести категориям с весами
  (`bot_crm 30`, `payments 25`, `site_analytics 15`, `servers 10`, `code 10`, `database 10`),
  счётчик «Требуют внимания».
- Карточки сгруппированы по категориям. В карточке: название, провайдер, статус проверки,
  маска ключа (`••••a91f`), «проверено N назад», меню: «Проверить», «Перевыпустить ключ»,
  «Отключить».
- Публичный SSH-ключ — с кнопкой копирования, рядом «установите его на сервере».
- Пустое состояние: «Подключите первый сервис» и кнопка добавления.
- Статусы: `pending` — «Проверяем», `ok` — «Работает», `warn` — «Работает с замечаниями»,
  `error` — «Не работает» + код причины текстом.

### 5.3 Карточка подключения

Что показывает: несекретный конфиг (URL, host, база, публичный ключ), что агент может и чего не
может (текст по `providerKey` из i18n), последняя проверка с расшифрованным кодом, журнал по
этому подключению (фильтр `connectionId` в журнале уже есть), история версий ключа (P1).

### 5.4 Добавление: один попап, три шага

Кнопка «Добавить доступы» открывает диалог на весь экран. Отдельного выбора «какой сервис» до
ввода нет: сервис определяет разбор, а не человек на первом шаге.

| Шаг | Что на экране                                                                                  |
| --- | ---------------------------------------------------------------------------------------------- |
| 1   | Поле ввода (textarea) + «Приложить файл» + необязательный комментарий «что это» + «Разобрать»  |
| 2   | «ИИ разбирает»: скелетон, через 2–5 с — результат разбора                                      |
| 3   | Разобранные группы (сервис, поля, маска, уровень доступа) и диалог по непонятному (раздел 6.5) |
| 4   | «Сохранить N подключений» → проверки идут фоном, статусы `pending`                             |

Форма по полям каталога остаётся запасным путём: она нужна для SSH (секрет генерируем мы) и для
тех, кто предпочитает заполнять явно. Она открывается из результата разбора («заполнить
вручную») и из каталога.

Ключевое правило: **текст и файл — один и тот же буфер**. Файл не отправляется отдельным
хранимым объектом, не остаётся на диске и не кэшируется; пользователь видит текст, который
будет разобран, и может его поправить.

## 6. Как работает разбор

### 6.1 Буфер и файлы

- Лимиты буфера: 64 КБ, 500 строк, 120 фрагментов. Превышение — ошибка до разбора
  (`CONNECTION_IMPORT_TOO_LARGE`), а не частичный импорт.
- Файлы: `.txt`, `.env`, `.md`. Браузер читает файл через `File.text()` и кладёт содержимое в ту
  же textarea — на сервер файл не уходит, отдельного хранилища и multipart нет.
- Расширение не проверяем: подходит любой файл, который читается как текст (`.csv`, `.json`,
  `.yaml`, `.log` — тоже). Бинарный файл отклоняется с `CONNECTION_IMPORT_FORMAT_UNSUPPORTED`:
  «Это не текст. Пришлите `.txt`, `.env` или `.md`». Таблицы `.xlsx`, PDF и картинки не
  разбираем: их конвертация — отдельная задача (раздел 12).
- Комментарий «что это» (`note`, до 500 символов) уходит модели как данные и помогает в спорных
  случаях: «это доступы к магазину на Тильде».

### 6.2 Фрагменты: что система вырезает из буфера

Буфер режется на фрагменты — минимальные единицы, которые можно назначить полю. Это чистая
функция в `packages/types/src/connection-import.ts`, одинаково покрытая тестами. Правила:

- `KEY=VALUE` и `export KEY=VALUE` — фрагмент `value` с `key`.
- `KEY: VALUE`, `KEY — VALUE`, `Логин: admin` — `key` = часть до разделителя, значение после.
- Строка из двух значений без разделителя (`admin qwerty`) — один фрагмент с частями `left` и
  `right`.
- PEM-блок (`-----BEGIN … END-----`) — один многострочный фрагмент, назначить его полю нельзя.
- Свободный текст: подпись до значения становится `label` («Пароль от админки»), хвостовая
  пунктуация срезается; значение без подписи остаётся фрагментом без `key`.
- Дубликат значения не создаёт второй фрагмент (совпадение по позиции, не по содержимому).
- У каждого фрагмента есть координаты: `{ line, part }`, где `part` — `value`, `key`, `left`,
  `right`.

Фрагмент никогда не «сохраняется как есть» и не является кандидатом в секретницу сам по себе:
он либо назначен полю провайдера, либо остаётся нераспознанным.

### 6.3 Что уходит модели

В запрос на разбор уходит **скелет буфера, а не значения**:

```jsonc
{
  "fragments": [
    {
      "id": "f3",
      "line": 4,
      "key": "YOOKASSA_SECRET_KEY",
      "shape": { "length": 40, "kind": "token", "prefix": "live" },
      "providerHint": "yookassa",
    },
    { "id": "f7", "line": 9, "label": "Пароль от админки", "shape": { "length": 9, "kind": "text" } },
    { "id": "f8", "line": 9, "shape": { "length": 6, "kind": "text" } },
  ],
  "note": "это доступы к магазину",
}
```

`shape` — длина, класс символов и первые 4 символа (те же 4 символа, что видны в маске
`••••a91f`). `providerHint` — результат детерминированного сопоставления по `envKeys`/`aliases`;
это подсказка, а не решение.

Значения в запрос не попадают никогда — ни в analyze, ни в clarify. Причины и отклонённые
альтернативы — в ADR 0002. Практическое следствие: если по именам и форме модель не может понять
сервис, она обязана спросить — это и есть нужное поведение, а не деградация.

### 6.4 Анализ моделью

Разбор выполняет worker: через `LlmService` в `RuntimeWorkerModule` идут все вызовы модели с
бюджетом и журналом (C17). Это архитектурное решение, а не отсутствие доступа к модели: провайдер
OpenAI уже реализован (`runtime/llm/openai.provider.ts`) и включается переменными окружения
`LLM_PROVIDER=openai` и `OPENAI_API_KEY` в `apps/api/.env`; ключ в репозиторий не попадает. API
ставит job `connections-import` и отдаёт `jobId`; UI опрашивает результат.

- Модель: `fast` (`LLM_MODEL_FAST`), `role: 'connections.import'`, `promptVersion: 'connections.import@1'`,
  `agentId: null`, бюджет — проектный. Один вызов на разбор.
- Промпт — версионированный код (`connections/import/connection-import.prompt.ts`), собирается из
  реестра: провайдеры, поля, `kind`, `required`, `envPrefix`, `envKeys`, `aliases`. Скелет буфера и
  комментарий подаются через `dataBlock()` как данные, не инструкции.
- Ответ — только вызов инструмента `propose_credentials`; свободный текст игнорируется. Аргументы
  парсятся zod'ом и проверяются кодом (C6, те же правила, что для инструментов агента).

```jsonc
// аргументы propose_credentials
{
  "items": [
    {
      "providerKey": "yookassa",
      "fields": [
        { "field": "shop_id", "fragment": "f3" },
        { "field": "secret_key", "fragment": "f4" },
      ],
      "confidence": "high",
    },
  ],
  "questions": [
    {
      "fragments": ["f7", "f8"],
      "text": "К какому сервису относятся эти логин и пароль?",
      "options": ["yandex_metrika", "telegram_bot", "unknown"],
    },
  ],
  "notes": ["В буфере два набора ключей Метрики — сохранён один"],
}
```

Проверки на сервере после ответа модели (`validateProposal`):

- `fragment` существует в скелете; иначе элемент отбрасывается, а фрагмент остаётся нераспознанным;
- `providerKey` есть в реестре, поле есть у провайдера; неизвестное поле или сервис — не сохраняется;
- обязательные поля покрыты; чего не хватает — попадает в `missing` и превращается в вопрос;
- один фрагмент не может уйти в два поля, одно поле — дважды;
- элементы на одного провайдера склеиваются в предпросмотре, а не создают второй подключение;
- неизвестный сервис — только вопрос или «пропустить» (в P1 — `generic`).

Результат (без значений) хранится в ответе job'а и отдаётся API:

```jsonc
{
  "items": [
    {
      "id": "i1",
      "providerKey": "yookassa",
      "fields": [
        { "field": "shop_id", "fragment": "f3" },
        { "field": "secret_key", "fragment": "f4" },
      ],
      "confidence": "high",
      "missing": [],
    },
  ],
  "questions": [{ "id": "q1", "fragments": ["f7", "f8"], "text": "…", "options": ["…"], "turn": 1 }],
  "notes": ["…"],
  "unmatched": ["f9"],
}
```

`confidence: 'low'` показывается в предпросмотре как «предположение» и требует подтверждения
человеком: сервис и поле можно поменять до сохранения.

### 6.5 Диалог уточнений

Диалог — не свободный чат, а карточки вопросов внутри попапа. У каждого вопроса есть:

- текст вопроса (модель пишет по-русски, без значений);
- варианты из каталога (`providerKey`) или полей провайдера — кнопками;
- «это не доступ» и «пропустить»;
- поле свободного ответа: «это ключ ЮKassa, магазин 12345».

Свободный ответ клиент очищает перед отправкой: вхождения его же значений из буфера заменяются на
`‹значение из буфера›`. Так человек не отправит модели секрет, даже если попытается.

Ход диалога:

1. Ответ-выбор (сервис, поле) разрешает вопрос без вызова модели — быстрый путь.
2. Свободный ответ уходит в `clarify` тем же job'ом с `mode: 'clarify'`: модель получает скелет
   спорных фрагментов, прошлое предположение и ответ как данные. Возвращает либо назначение,
   либо следующий вопрос.
3. Ходов может быть несколько; в любой момент доступно «назначить вручную» (селекты полей).
4. Ответы не покидают вкладку: сессия разбора живёт в памяти до сохранения (C21). Перезагрузка
   теряет несохранённое — это осознанная цена за то, что значения не лежат на сервере.

Пока диалог открыт, уже разобранные группы видны и доступны: можно сохранить понятное и
вернуться к остальному позже.

### 6.6 Предпросмотр и сохранение

Предпросмотр собирается в браузере: фрагменты + назначения модели → группы по сервисам. Значения
показываются только маской. По каждой группе: чекбокс «подключить», уровень доступа
(`read`/`read_write` из `accessLevels` провайдера), «не хватает: shop_id».

При сохранении клиент отправляет по каждой группе **поля с реальными значениями** — так же, как
это делает сегодняшняя форма создания. Модель в записи не участвует и значений не видела. Сервер:

- заново валидирует поля (`splitFields`) и уровень доступа;
- переиспользует `prepare`/`insertConnection`/`rotate`, чтобы не появилось второго пути записи
  секрета и второго места, где можно забыть журнал;
- ставит проверки в очередь и возвращает `pending`.

Частичный успех нормален: из пяти групп четыре созданы, одна отклонена с кодом и полем. Режимы
при уже существующем подключении того же провайдера: `skip` (по умолчанию, результат `skipped`)
или `replace` (новый ключ через `rotate`, старый живёт 5 минут, результат `replaced`). Повторная
отправка того же буфера даёт `unchanged`.

После сохранения буфер очищается, диалог закрывается, список обновляется; статусы обновляются по
SSE `/stream` (уже есть) или поллингом раз в 3 секунды.

### 6.7 Если модель не ответила

Разбор — не критический путь. В разработке по умолчанию стоит `LLM_PROVIDER=fake`, в бою —
`openai` с ключом из env. Если модель не ответила (таймаут, 429, ошибка провайдера), исчерпан
бюджет (`LlmBudgetExceededError`) или включён `fake` без фикстуры:

- UI показывает баннер «ИИ недоступен — разбираем по правилам»;
- работает детерминированное сопоставление по `envKeys`/`envPrefix`/`aliases` из `packages/types`;
- остальное человек назначает селектами вручную;
- сохранение работает всегда: `POST …/connections/import` не требует модели.

Тот же путь включается галочкой «не отправлять в ИИ» в попапе — для тех, кто не хочет отдавать
даже скелет буфера.

## 7. API

Все маршруты — под `/v1/accounts/:accountId/projects/:projectId/connections`, роль `tech` и выше,
отдельный `StrictThrottle`. Требуется правка whitelist-регэкспа в
`apps/web/src/app/api/v1/[...path]/route.ts` (C5) для `import`, `import/analyze`,
`import/analyze/:jobId`, `import/clarify`.

| Метод и путь                  | Назначение                                                 | Ответ                                |
| ----------------------------- | ---------------------------------------------------------- | ------------------------------------ |
| `POST …/import/analyze`       | скелет буфера → job разбора                                | `202 { jobId }`                      |
| `GET …/import/analyze/:jobId` | статус и результат разбора                                 | `200 { status, result?, error? }`    |
| `POST …/import/clarify`       | ответ человека на вопрос → следующее назначение или вопрос | `200 { item?, question?, done }`     |
| `POST …/import`               | сохранение групп с реальными значениями                    | `200 { items, unmatched, warnings }` |

```jsonc
// POST …/import
{
  "groups": [
    {
      "providerKey": "yookassa",
      "accessLevel": "read",
      "fields": { "shop_id": "123456", "secret_key": "live_…" },
    },
    { "providerKey": "telegram_bot", "accessLevel": "read_write", "fields": { "bot_token": "123…" } },
  ],
  "mode": "skip",
}
```

```jsonc
// ответ
{
  "items": [
    {
      "providerKey": "telegram_bot",
      "outcome": "created", // created | replaced | skipped | unchanged | failed
      "connection": { "id": "…", "status": "pending", "credential": { "masked": "••••a91f" } },
      "error": null,
    },
    {
      "providerKey": "postgres",
      "outcome": "failed",
      "connection": null,
      "error": { "code": "CONNECTION_FIELDS_INVALID", "field": "password" },
    },
  ],
  "unmatched": ["REDIS_URL"],
  "warnings": [{ "code": "CONNECTION_IMPORT_FRAGMENT_UNKNOWN", "lines": [9] }],
}
```

Изменения в существующих контрактах:

- `ProviderField` получает `envKeys`/`aliases`, `ProviderDefinition` — `envPrefix`, `aliases`,
  `docsUrl`; всё отдаётся в `GET /v1/connection-providers` (нужно и модели, и фолбэку).
- `packages/types/src/connection-import.ts`: схема фрагмента, `buildFragments()`,
  `matchFragments()` (детерминированный пре-пасс), zod-схемы analyze/clarify/import.
- Клиент: `packages/api-client/src/project-operations.ts` — `analyzeImport`, `clarifyImport`,
  `importConnections`.

Очередь `connections-import` (`queues/queues.ts`): `attempts: 1`, результат хранится час,
payload и результат — без значений. Processor берёт аккаунт из CLS так же, как
`connection-check.processor.ts`.

## 8. Данные

- Миграций не требуется: `connections`, `connection_credentials`, `connection_links` уже есть.
  Алиасы, `docsUrl` и каталог для модели — код реестра, не таблица.
- Значения не пишутся ни в одну новую таблицу: разбор и диалог живут в памяти вкладки.
- `llm_calls`: по строке на вызов (`role: 'connections.import'`, `agent_id null`, токены и
  стоимость). Содержимое промпта и буфера не пишется — только роль, версия промпта, результат.
- Журнал: одна запись `connections.import` с `{ groups, created, replaced, skipped, fields }` —
  только имена полей и счётчики, без значений. Плюс существующие `connections.create` на каждое
  подключение.
- Redis (payload и результат job'а) содержит только скелет: имена, подписи, маски и координаты.
- P1: `connection_credentials.expires_at` заполнять, если провайдер объявит TTL; до этого убрать
  `expiring/expired` из DTO.
- Существующий частичный индекс `connections (project_id) WHERE deleted_at IS NULL` достаточен
  для дедупликации на десятках подключений; отдельный индекс `(project_id, provider_key)` — P2.

## 9. Безопасность

Модель угроз для ввода доступов: (1) секрет утекает в лог/ответ/Redis/модель; (2) текст буфера
управляет моделью (prompt injection); (3) модель придумывает сервис или значение; (4) человек
сохраняет не то, что думал.

Чеклист на ревью:

- Значение секрета не возвращается ни в одном ответе: только `masked` (`••••` + 4 последних
  символа, для коротких — просто `••••`). Модель видит только маску-скелет (раздел 6.3).
- Значения не попадают в payload и результат BullMQ и в `llm_calls`; e2e проверяет это по JSON
  job'а и по строкам `llm_calls`.
- Тело запроса не логируется: `text`, `fields`, `password`, `token`, `secret` —
  в redaction; ошибки — только `{ code, field }`, без значений и фрагментов буфера.
- Текст буфера подаётся модели только как `dataBlock(untrusted(…))`; ответ модели — только
  вызов инструмента, аргументы — zod и серверные проверки. Модель не может назвать значение:
  она возвращает координаты (`fragment`, `part`), значения подставляет клиент.
- Ничего не сохраняется автоматически: запись — только по кнопке после предпросмотра; `low`
  confidence помечен и требует подтверждения.
- Лимиты: 64 КБ / 500 строк / 120 фрагментов на буфер, throttle на все маршруты,
  `Cache-Control: no-store`.
- Роль `tech` и выше; `viewer` не видит ни список ключей, ни маски; CSRF-заголовок
  `x-geniebox-request` уже проверяется прокси для всех не-GET запросов.
- Браузер: `autoComplete="off"`, `spellCheck={false}`, без `localStorage`, `sessionStorage` и
  кэша react-query (`gcTime: 0`), очистка при закрытии и после сохранения, предупреждение
  «вставляйте только на своём устройстве».
- Файл читается в браузере и на сервер не уходит: в запросах нет multipart, base64 и временных
  объектов в хранилище.
- Секреты агентам: агент видит только `config` и результат проверки, расшифровка — в
  `ConnectionSecrets` внутри worker'а, в памяти одного вызова.

## 10. Тесты

- unit (`packages/types`): `buildFragments` — 20 кейсов (dotenv, `export`, `KEY: VALUE`,
  «логин пароль», PEM, URL с userinfo, русские подписи, кавычки, CRLF/BOM, дубликаты, лимиты).
  `matchFragments` — алиасы, префиксы, конфликты.
- unit (`apps/api`): валидатор назначений — неизвестный фрагмент/поле/провайдер, непокрытое
  обязательное поле, два поля на фрагмент, два элемента на провайдера.
- unit (`apps/api`): сборка промпта не содержит ни одного значения из буфера (проверка по
  фикстуре), фрагменты идут только внутри `dataBlock`.
- unit: `FakeProvider` для `connections.import` отдаёт фикстуру `propose_credentials` (C18).
- integration: analyze с `fake` → назначения и вопросы; poll до `done`; clarify → назначение;
  import → 2 созданы, 1 `skipped`; значения не встречаются в ответе, в `llm_calls`, в payload
  job'а и в БД открытым текстом; `viewer` → 403; чужой аккаунт → 404; 64 КБ → 400;
  бюджет исчерпан → `degraded`, импорт всё равно работает.
- UI — вручную по сценариям раздела 4 (автотестов на ввод секретов в спринте не пишем).

## 11. Этапы

**P0 (до демо):** C1–C7, C17–C18 и полный путь: попап, фрагменты, разбор моделью, диалог,
предпросмотр, импорт. Это один экран, одна очередь, один промпт с инструментом, один эндпоинт
сохранения и подсказки в реестре.

**P1:** ссылка разработчику в UI (C10), история версий ключа, тексты кодов проверки (C13),
`docsUrl` (C12), переупаковка KEK (C11), провайдер `generic` (C20).

**P2:** возобновляемая сессия разбора (C21), идемпотентность импорта (C14), TTL ключей (C8),
несколько экземпляров одного провайдера, разбор `DATABASE_URL` (C22).

## 12. Что не входит

- Передача значений модели — ни при каких настройках: это кладёт секреты в Redis, в логи
  провайдера и в историю, а диалог решает ту же задачу (ADR 0002).
- Таблицы `.xlsx`/`.xls`, PDF и картинки: их конвертация в текст, OCR и разбор архивов — отдельная
  задача.
- Внешний секрет-менеджер (Vault, AWS Secrets Manager): KEK уже вне БД.
- Общий доступ к подключению между проектами и передача секрета другому человеку.
- Показ сохранённого секрета в UI (re-veal) и экспорт секретов.
- Автоматическое обновление OAuth-токенов и синхронизация с внешним каталогом сервисов.
